## 2026-11-04 | M2 返修 3:脚印菱形碰撞(用户三次反馈"碰撞箱只有方块中间")

**用户反馈**:墙面碰撞箱不是整个方块,只有方块中间才挡人,要走进方块里才被挡——仍有一点穿模。

**根因**:立起物碰撞体用的是小矩形(48×14 等),只覆盖菱形脚印的中带;视觉底面菱形(64×32)比碰撞区大,脚要越过底面边缘 ~9px 才碰到碰撞。

**修复**:全部立起物碰撞统一为**脚印菱形 ConvexPolygonShape2D**(±32,0 / 0,±16),与视觉底面逐像素一致;顺带移除此前两个补丁(M1 的边界内移矩形、M2 的横墙线段矩形)——菱形一圈自然密封房间,行为更简洁。门 Blocker 同步改菱形。像素级验证:玩家贴墙时脚底停在视觉底边线 ~1px 处。

**工具链教训(两条)**:
1. **手改 .tscn 改了 sub_resource 的 id,必须同步改所有引用**(门 Blocker 改名后节点还引用旧 id → 场景加载失败);
2. **headless `-s` 构建脚本若运行时错误导致 quit() 不可达会无限挂起**(占住终端直到超时)——构建/冒烟脚本必须保证 quit 可达,调用侧一律加 `timeout`。
3. 另:GDScript `const` 不能用 `PackedVector2Array(...)` 构造表达式,改用 `static var`。

**关于"是否安装 Godot 辅助 skills"(用户问)**:暂不需要。两类 bug 的真正根因是"验证只看节点状态、没看渲染与几何",本仓库已自建验证闭环(状态打印 + 截图 + 像素探针 + 冒烟场景),比通用工具更贴合;规范层面已固化(Y-sort 锚点、脚印碰撞)。后续到 M3 若记录/回放需要自动化回归,再引入 gdUnit4;godot:cli / godot:setup skills 已在环境中备查。

**下一步**:用户重测 → M2 关闭 → M3。

## 2026-11-04 | M2 返修 2:墙体 Y-sort 排序基准错误(用户二次反馈"墙躺倒穿模")

**用户反馈**:部分立起的贴图像"放倒的",仍会穿模——特别是下面的周界墙、横墙靠下的半边。

**根因**:`_make_wall` 把 64×80 立体贴图的脚印偏移(−24px)直接烘进了**节点 position**(`position = 格位 + (0,-24)`)。Y-sort 按**节点 y** 排序,于是这些墙的排序点跑到了脚印以北 24px——排序点落进玩家可走区域的 y 范围,玩家在墙后(北)却 y 值更大而画在墙前,墙体视觉上"躺倒被穿过"。只有排序点被推进可走区的墙出问题(下墙、横墙下半),与用户描述完全吻合。

**修复**:偏移改用 `Sprite2D.offset`(仅影响绘制,不改变节点 position)——排序基准回到脚印格位。build_dev_mechanisms 的 `_make_wall` 已改;build_dev_room 的 `_make_block` 本就以 StaticBody2D 为排序节点,无需改。

**验证**:冒烟新增场景 C(玩家向右下压进底墙):玩家正确地被站立墙立方体遮挡(仅露少许),墙体顶面/侧面读数正常;A/B 状态数据不变(开关黄/门开绿灯/门关红灯)。

**经验**:2D 等距中,**视觉偏移一律用 Sprite2D.offset,不动 position**——position 是逻辑与排序的唯一锚点。此规则后续写进 docs/03。

**下一步**:用户重测 TC-03~07 → M2 关闭 → M3。

## 2026-11-04 | M2 返修:影子副本 / 横墙碰撞 / 等距立方体贴图(用户验收反馈)

**用户验收发现三个问题,排查后根因如下:**

**问题 1(最严重):开关/门"无反应"。** 根因是 **pack() 展开实例子场景产生影子副本**:
- `_assign_owner` 此前把子场景实例的内部节点(Panel/Light/Pad 等)也设置了 owner=场景根;
- pack() 遇到"owner 指向打包根、但父级是实例"的节点,会按「可编辑子节点」平铺进 .tscn;
- 运行时实例化:子场景自身的脚本驱动节点(改名 @Panel@ 等内部名)+ 平铺的静态节点**并存**;
- 结果:真开关变黄被静态白底座盖住、真门体抬起被静态关门面板盖住——**物理状态是对的,渲染是错的**,用户看到"无反应";
- 我的自动化验证只读了脚本驱动的节点状态(全对),没验证"实际渲染的是什么"——**状态正确 ≠ 渲染正确**,验证必须含渲染证据(像素探针/截图)。
- 修复:owner 只赋给无主节点(`child.owner == null` 才赋),实例保持干净引用;重建后门仅 3 个具名子节点,重复消失。

**问题 2:横墙可以穿过。** 占位墙此前只有外观没有碰撞(设计上只有周界+门有)。已补:沿网格行两段旋转矩形夹住门洞(`_add_wall_segment`,端点外延 16px 盖住端点菱形)。

**问题 3:立起物贴图是正面平贴,不符合 2.5D。** 用户判断正确。重画为**真等距立方体**:64×80,脚印菱形中心 (32,64),顶面菱形 + 左右两个 2:1 斜面(左受光右背光);墙体/测试方块/门体全部换用;精灵上移 24px 使脚印对齐节点原点(Y-sort 基准不变);门体开合参数改为 −24(关)/−58(开)。

**备注**:角色占位贴图暂保持面向镜头的 billboard——2D 等距游戏的角色惯例(如 Hades),四向像素稿随正式美术阶段制作,不属于缺陷。

**验证**:引擎状态四证据 + 门子节点树(仅 3 个具名子节点)+ 截图(黄底座/抬升门体/绿灯/立方体墙面)全部通过。

**下一步**:用户重测 TC-03~07(建议先在 Godot 中「项目 → 重新加载当前项目」刷新会话状态)→ M2 关闭 → M3。

**问题与决定**:
- **冒烟脚本必须按物理帧计数**:`await process_frame` 在无垂直同步窗口下约 180fps,与 60Hz 物理帧脱节,24 渲染帧只走了 8 物理帧(移动量差 2.9 倍)导致首次冒烟误判;改用 `await physics_frame`;
- **PackedScene.pack() 不保存运行时建立的信号连接**(.tscn 无 [connection] 段):开关→门连线改由场景根脚本 `dev_mechanisms_room.gd` 在 `_ready` 完成——与 Level_01 将由 LevelManager 连线的方案一致;
- headless 模式下 `-s` 脚本 + `await process_frame` 会挂起(帧循环不推进),冒烟脚本一律窗口模式运行;
- `%DoorHole` 漏标 `unique_name_in_owner` 导致 `%` 引用解析失败——手写场景时唯一名标记需逐一核对(已在 dev 冒烟中即时暴露并修复)。
